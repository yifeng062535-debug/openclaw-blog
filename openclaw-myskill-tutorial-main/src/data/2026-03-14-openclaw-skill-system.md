OpenClaw 里最有价值的设计之一，就是技能系统。

技能可以理解成一份本地化的操作说明书，它告诉代理：

- 什么场景该触发。
- 应该读哪些文件。
- 应该遵循什么步骤。
- 有哪些额外资源、脚本或模板可以复用。

这让“经验”从一次性的对话内容，变成了**可持续调用的项目能力**。

## 为什么技能比复制提示词更靠谱

复制提示词的问题在于，它离代码和文件系统太远。你可以描述一个流程，但没法保证每次都按同样的结构执行。

技能则不一样：

- 它是落在磁盘里的。
- 它可以引用本地脚本和模板。
- 它可以限制代理读取的范围。
- 它可以在不同仓库里重复使用。

所以技能本质上不是“更长的提示词”，而是**一种可执行工作协议**。

## 一个技能通常包含什么

典型的技能会说明：

1. 触发时机。
2. 必须读取的 `SKILL.md`。
3. 相关脚本和资源目录在哪里。
4. 输出格式应该是什么。
5. 如果技能受阻，应该如何降级处理。

例如，一个处理视频转码的技能，可能会要求代理：

- 先扫描指定目录。
- 找到所有 `dist` 目录。
- 批量转成 `.webm`。
- 保留原始文件。
- 最后汇总每个文件的结果。

这就是一个非常典型的“高频动作固化”。

## 技能的真正价值：减少上下文浪费

如果一个流程你每次都要重新解释，代理就必须每次重建同样的上下文。

技能的作用就是把这部分成本前置掉。只要触发条件匹配，OpenClaw 就会优先读取技能，再按技能描述工作。

这会带来两个结果：

- 更稳定。
- 更省 token。

## 怎么判断一个动作值不值得做成技能

我一般看三点：

- 是否会反复出现。
- 是否有明确步骤。
- 是否依赖本地脚本或项目约束。

如果答案大多是“是”，就很适合变成技能。

## 写技能时最容易犯的错

最常见的错不是写得不够长，而是写得太散。

一个好技能应该尽量做到：

- 触发条件明确。
- 流程按顺序写。
- 引用的路径准确。
- 失败时有 fallback。

坏技能通常像这样：

```text
如果用户想处理媒体资源，就帮他处理。
```

这种描述几乎没有执行价值。

更好的写法是：

```text
当用户要求扫描某个根目录并批量转换 dist 目录里的 mp4 为 webm 时，使用此技能。
先打开 SKILL.md。
如果有 scripts/，优先运行脚本。
输出转换前后统计和逐文件结果。
```

## 在 OpenClaw 项目里怎么配合技能使用

比较高效的做法是：

1. 先把通用流程技能化。
2. 在 `AGENTS.md` 里声明触发规则。
3. 让代理在匹配场景时自动读取技能。

这样以后遇到同类任务，代理就不会重新发明流程。

## 一个很重要的认知

技能不是为了把代理“限制死”，而是为了让它把精力花在真正需要判断的部分。

固定流程靠技能。
项目差异靠现场判断。

这个分层做对了，代理的稳定性会明显提升。

## 小结

当你开始把高频动作写成技能，OpenClaw 的能力就不再是“一次性聪明”，而是“可沉淀的生产力”。
