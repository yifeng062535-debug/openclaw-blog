OpenClaw 不是一个“会聊天的界面”，而是一个**在代码仓库里持续完成任务的执行代理**。你给它目标，它会先读环境，再拆任务，然后直接做修改、验证结果、整理交付。

如果你第一次接触它，最容易踩的坑不是不会下指令，而是**一下子给太宽的目标**。OpenClaw 的效率来自上下文密度，所以你要先让它知道三件事：

1. 当前仓库里已经有什么。
2. 你希望它产出什么结果。
3. 你对技术边界的约束是什么。

## 先建立最小任务闭环

可以把一次交互理解成下面这条链路：

```text
目标 -> 读取仓库 -> 理解约束 -> 制定修改路径 -> 执行 -> 构建验证 -> 交付
```

真正高效的地方在于，OpenClaw 不会停在“建议阶段”，它会直接进入执行阶段。这意味着你提需求时最好写得像任务单，而不是像聊天。

例如：

```text
用 Astro 初始化一个纯前端博客。
保留标签、分页和搜索。
整体风格做成科技感的 OpenClaw 教学站。
补 3 到 5 篇 OpenClaw 中文教程文章。
最后跑构建并告诉我结果。
```

这类表述的优点是：

- 目标可验证。
- 边界清晰。
- 结果是代码而不是建议。

## OpenClaw 为什么先看仓库

经验不足的人会以为代理直接开始写更快，但这通常会把项目带偏。OpenClaw 先读目录、配置文件、依赖和关键入口，是为了判断：

- 这是空仓库还是已有工程。
- 团队已经采用了什么技术栈。
- 有哪些本地约束，比如 `AGENTS.md`、`SKILL.md`、构建脚本或风格规范。

这一步是“避免误改”的核心。

> [!TIP]
> 如果仓库里存在 `AGENTS.md`，先让 OpenClaw 按它工作。这样能减少无效往返。

## 最适合给 OpenClaw 的任务类型

最适合的任务通常有这些特征：

- 可以通过代码或命令验证结果。
- 涉及多个文件，但目标比较明确。
- 需要在现有仓库里保持风格一致。
- 最终交付是一个可运行结果，而不是泛泛解释。

比如这些都很合适：

- 初始化一个静态博客并填充内容。
- 给现有页面改版并保持原有路由结构。
- 补一条完整的数据流和表单校验。
- 写几篇教程文档并接入内容系统。

## 一个标准的执行节奏

你通常会看到它这样工作：

1. 先发一个简短说明，告诉你它要检查什么。
2. 读取仓库和关键文件。
3. 如果任务较大，会整理一个简短计划。
4. 执行代码修改。
5. 跑构建或测试。
6. 汇总改动和剩余风险。

这个过程跟一个靠谱的工程师很像，差别在于它能在一个回合里把大部分落地工作做完。

## 开始时不要追求“完美提示词”

你不需要把提示词写成论文。比起“写得华丽”，更重要的是：

- 约束够具体。
- 输出够明确。
- 能让任务一次收束。

一个很实用的模板是：

```text
在当前仓库里完成 X。
必须满足 A、B、C。
不要做 D。
完成后执行 E，并告诉我结果。
```

## 这篇文章的结论

如果你想把 OpenClaw 用顺手，记住一句话：

**先给可执行目标，再让它自己进仓库建立上下文。**

一旦这个闭环跑通，它就不是“问答工具”，而是你项目里的执行位。
